## 三、已确认的 Bug（线上正在发生）

### 3.1 Service Worker 缓存穿透 → SW 安装失败 → PWA 离线功能为零（严重度：Critical）

**根因**： `sw.js:3-14` 预缓存列表写的是无参数路径（`./app.js`），但 `index.html:59` 引用的是 `app.js?v=9`。Cache API 的缓存键包含完整 URL（含 query string），`caches.addAll()` 缓存 `/app.js`，浏览器请求 `/app.js?v=9`——不匹配。`addAll()` 是原子操作，一个资源失败整个 Promise reject，SW install 阶段失败，永远不会激活。

**线上验证**： `navigator.serviceWorker.getRegistrations().then(r => r.length)` 返回 `0`。

**影响链**： SW 未注册 → 无离线缓存 → 每次冷启动都要从网络加载 812KB stations.json → 慢网用户体验差 → "PWA"名存实亡。

**修复**： 三选一：
1. 预缓存列表也加 `?v=9`（跟随版本号，但每次发版要改两处）
2. SW fetch 拦截时 `caches.match(e.request, {ignoreSearch: true})`（推荐，一劳永逸）
3. 去掉 `?v=9`，改用 content-hash 文件名（最工程化，但需要构建步骤）

### 3.2 模态框 Escape 键不关闭（严重度：低）

`app.js:201-204` 的 Escape 处理只清空了搜索框，没有关闭模态框。ARIA `role="dialog"` 要求 Escape 可关闭。键盘用户打开关于弹窗后无法关闭（只能 Tab 到"閉じる"按钮）。

### 3.3 搜索框双清除按钮（严重度：低）

`input type="search"` 在 WebKit/Blink 渲染原生 ✕，自定义 `#clearBtn` 也显示 ✕。截图确认两个并排。修复： CSS 加 `#q::-webkit-search-cancel-button { -webkit-appearance: none; }`。

### 3.4 详情页打开时结果列表不收起（严重度：低）

`openDetail()` 调 `scrollIntoView` 把详情卡片滚到视口，但结果列表仍在上方，sticky-top 搜索框覆盖在结果上造成视觉重叠。应该打开详情时折叠结果列表或自动滚动到详情区域。

## 四、数据问题（深层分析）

### 4.1 819 个无读音站的画像

不是所有站都"平等地缺读音"。缺失呈现明显的地域聚集：

| 都道府県 | 无读音站数 | 占该县总站点比例（推算） |
|---------|-----------|----------------------|
| 愛知県 | 103 | ~12% |
| 北海道 | 81 | ~8% |
| 高知県 | 67 | ~40%+ |
| 広島県 | 56 | ~15% |
| 大阪府 | 55 | ~6% |

高知県的读音覆盖率可能不到 60%。愛知県（名古屋都市圈）缺失 103 站——这不是偏远山区的问题，是城市通勤圈的问题。

**根因推测**： Wikidata P1814 和 OSM name:ja-Hira 的覆盖率本身就有地域偏差（城市 Wikidata 编辑者多，覆盖率反而应该高——所以更可能是匹配逻辑的问题）。需要逐源分析： 这 819 站中，Wikidata 有 kana 但匹配失败的有多少？OSM 有 name:ja-Hira 但匹配失败的有多少？pykakasi 能正确读的有多少？

### 4.2 高田馬場的读音去哪了

高田馬場（たかだばばば）是东京山手线+西武新宿线+东西线的大站，42.3万人/日。Wikidata 上一定有读音。缺失说明**匹配逻辑有 bug**——可能是：
- 站名不匹配（Wikidata 写「高田馬場駅」，ekidata 写「高田馬場」，normalize 后应该一致）
- 坐标距离阈值过严（Wikidata 坐标与 ekidata 坐标有微小偏差）
- P1814 属性在非日语 label 上

这需要具体 debug 匹配链路，不是"补数据"能解决的。

### 4.3 站数缺口 1,026 站

SPEC 声称 ekidata 有 10,887 站（运行中 10,464），最终输出 8,974。差异 1,490 站。可能的流失点：
- `e_status == '0'` 过滤（废弃站）
- 同组异名拆分逻辑把某些站合并了
- 某些站缺少必要字段被静默跳过

`build_data.py` 没有任何过滤日志。需要加 `print()` 追踪各阶段数量。

### 4.4 客流数据年份分布

95% 的站使用 2019 年数据。SPEC 选择了 2015-2019 窗口（疫情前），这在 2026 年已经 7 年了。S12-25 数据集本身包含 2011-2024 年共 14 年数据，2024 年数据已经可用。继续用 2019 年数据排序，在疫情后客流恢复不均衡的背景下，会导致排序失真——远程办公普及率高的站点（如丸之内、新宿副都心）恢复慢，而住宅区站点（如北千住、蕨）恢复快。用 2019 年数据排序会把前者排得过高。

### 4.5 罗马音短前缀可找到性（验证报告数据）

| 前缀长度 | 罗马音命中率（前10名） |
|---------|---------------------|
| 1 字母 | **0/40** (0%) |
| 2 字母 | **5/40** (12.5%) |
| 3 字母 | 17/40 (42.5%) |
| 4 字母 | 29/39 (74.4%) |

输入 "sh" 找不到新宿。输入 "ta" 找不到高田馬場。这是 rid 排序的固有缺陷——短前缀匹配集太大（可能 500+ 站），高客流站永远排在前面，目标站被挤出前 10。

当前实现没有"精确匹配优先"机制。输入 "shinjuku" 时新宿排第一（精确匹配），但输入 "sh" 时新宿可能排第 200 名。

## 五、性能深层分析

### 5.1 buildIndex 105ms 的实际影响

桌面 Node.js 实测 105ms，但在 Lighthouse 的 4x CPU 节流模拟下变成 1,120ms TBT。对 iPhone 17 Pro 用户可能无感，但对低端 Android（目标用户群的另一半）是明显的卡顿。

**优化路径**：
1. **预计算索引**： 构建时把排序后的索引序列化为二进制，前端直接 `new Uint32Array(await res.arrayBuffer())`。28,011 个条目，每个条目 ~20 字节，约 560KB。可以把 buildIndex 从 105ms 压到 <5ms
2. **延迟构建**： 先渲染空搜索框，用 `requestIdleCallback` 或 Web Worker 后台构建索引。用户看到搜索框可输入时索引可能还没好，但用户通常需要 1-2 秒才会输入第一个字
3. **增量索引**： 只索引前 N 个高频站的完整键，其余站惰性索引

### 5.2 search() 的 O(n) 扫描

`search.js:122-124`： 前缀匹配拿到 id Set 后，遍历全部 8,974 站（stations 数组已按 rid 排序）找交集。对单字符查询（如 "し"，命中 500+ 站），每次都要扫完全部数组。

**实测**： 平均 0.1ms/次（桌面）。但在 Moto G4（Lighthouse 基准设备）上可能 1-3ms。加上 40ms debounce，用户体验是"输入后 40-43ms 出结果"——可接受但不极致。

**优化**： stations 数组本身按 rid 排序，匹配结果天然按 rid 排序。不需要扫描全部——用二分找到 rid 排名的分界点，只扫描前 N 个候选。或者，给每个 entry 预计算 `ridRank`，匹配时按 ridRank 排序取前 50。

### 5.3 stations.json 812KB 传输

Brotli 压缩从 3.1MB → 812KB（73.8% 压缩率），效果不错。但 812KB 仍然是最大单资源。进一步优化：
- 去掉 `per` 明细字段（约占总量的 30-40%），改为按需加载单个站的明细
- 用 MessagePack 替代 JSON，可再减 20-30%
- 分片加载： 按五十音图分 10 片，首屏只载あ行+か行+さ行

## 六、架构与工程

### 6.1 值得肯定的设计决策

- **纯函数搜索**（search.js）： 无 DOM 依赖，node:test 直接跑，TDD 友好
- **数据管线模块化**： ekidata/s12/kana/colors 各自独立，有测试
- **数据诚实**： meta.json 有 sha256、字节数、覆盖率；验证报告有种子可复现
- **同组异名站拆分**： 正确解决了モノレール第1/第2航站楼等合并错误
- **系统性机场别名**： 从英文名数据驱动生成日语别名，不是手工列举
- **不变量断言**： `roma == kana2roma(kana)` 对每个站成立

### 6.2 工程缺陷

**无构建工具链**（SPEC 7.2 明确要求 `make data`）：
- 无 Makefile
- 无 requirements.txt（opencc 依赖只存在于 SPEC 声明中）
- 无 package.json
- 无 CI
- 版本号手动管理（`?v=9` 出现在 4 个文件中，每次发版手动改 4 处）

**代码残留**：
- `s12.py:15` 和 `s12.py:58` 定义了两个 `load_s12()`，第二个覆盖第一个
- `join_ridership()` 内部调 `load_ekidata()`（:74），但 build_data.py 已经加载过一次——重复 IO
- `normalize.py:137` 有一行死代码： `ou = base.replace(...) if False else None`

**双端逻辑漂移风险**： `normalize.py`（Python）和 `search.js`（JS）各自实现了归一化。目前一致（有测试保障），但未来改动一边忘改另一边就是静默数据错误。canon.json 有 3,863 个键，其中 2,324 个是冗余的（不在任何站名/线路名中出现）——说明 canon 生成逻辑可能过于宽泛，或者是旧数据的残留。

## 七、UI/UX 深层评价

### 7.1 设计哲学判断

这个 UI 的设计方向是**正确的**——极简搜索、信息层级清晰、无装饰性元素。它让我想起了早期的 Google： 一个框，一个按钮，结果说话。在"駅さがし"这个任务上，这比任何花哨的地图界面都更高效。

但执行上有几个**未完成**的地方：

### 7.2 空态与无结果态的不对称

空态（未输入）有 5 个示例 chips 引导。无结果态只有一行"該当する駅が見つかりません"。用户搜索 "渋谷"（简体）找不到时，没有提示"试试「渋谷」或「しぶや」"。这是引导链断裂的地方。

### 7.3 详情页缺少"返回"

打开详情后，没有"戻る"按钮或手势。用户必须清空搜索框或按浏览器返回键（但返回键会直接离开页面，因为没有 history.pushState）。在手机上这是一个高频操作，当前的交互成本太高。

### 7.4 颜色对比度 FAIL

Lighthouse 报告颜色对比度不足。最可能是 `--text-3: #9a9aa0`（浅灰）在白色背景上对比度不足 4.5:1。`--text-2: #6e6e73` 刚好过线。`--text-3` 用于 hint 文字、单位标注等，虽然信息重要性低，但 WCAG AA 要求所有文本都达标。

### 7.5 关于按钮的"i"

32px 直径，斜体 "i"，在页面右上角。这个按钮承载了"数据可信度"的全部信息（数据来源、口径、限制），但视觉上过于低调。考虑到这个应用的核心竞争力是数据的准确性和透明度，关于按钮应该更突出——或者至少在首次访问时有一个微妙的高亮提示。

### 7.6 加载体验

SPEC 说"加载中仅显示细进度条"，实际连进度条都没有。footer 的"読み込み中…"文字在视口最底部，首屏完全看不到加载状态。812KB 的 stations.json 在 4G 下需要 2-3 秒，用户盯着空白页面不知道发生了什么。

## 八、兼容性

- **字体栈**： `-apple-system → Hiragino → Noto Sans JP → Yu Gothic`，覆盖面好。Linux 无 Noto Sans JP 时回落 sans-serif 可能不支持日语字符（现代发行版大多预装）
- **CSS**： `dvh`、`inset`、`gap`（flex 上下文）需要 Safari 15.4+。目标用户 iPhone 为主可接受，但无 `@supports` fallback
- **JS**： ES Module 需要 Safari 10.1+。无 `nomodule` fallback
- **ARIA**： combobox 模式在 VoiceOver/TalkBack 上的实际表现未测试。`aria-activedescendant` 未设置（键盘导航只改 CSS class，屏幕阅读器不知道当前高亮项）
- **robots.txt**： Lighthouse 报告 56 个错误——需要检查具体内容

## 九、安全

- **XSS 防护到位**： 所有用户可见数据经过 `escapeHtml()`
- **无 CSP header**： 纯静态站点风险低，但 `default-src 'self'` 是免费的
- **外部链接**： `rel="noopener"` 都有
- **SW 缓存投毒**： `ignoreSearch: false` 意味着 `?v=evil` 会被缓存为独立条目（低风险但值得注意）

## 十、可实践建议

1. **修复 Service Worker 缓存穿透**：SW fetch 拦截改用 `caches.match(e.request, {ignoreSearch: true})`。这是一行代码的修复，让 PWA 离线功能从"不存在"变成"可用"
2. **debug 高田馬场等 819 站的读音缺失根因**：逐源检查 Wikidata/OSM 的匹配失败原因——是站名不匹配、坐标距离过严、还是数据本身缺失。高田馬場（42万人/日）没有读音说明匹配逻辑有 bug，不是数据缺口
3. **提升读音覆盖率至 ≥99%**：基于 #2 的根因分析修复匹配逻辑；对仍缺失的站用 pykakasi 生成候选 + 人工抽查客流前 200 站；从 Wikipedia 日语版 API 批量拉取 `{{読み}}` 模板补充
4. **追查 1,026 站缺口**：在 `build_data.py` 加各阶段过滤日志（ekidata 总数 → active → 组拆分 → 最终输出），确认流失原因；如果是 ekidata 2022-09 快照固有的（新站缺失），更新 SPEC 并加注
5. **修复搜索短前缀排序**：对前缀匹配结果集 ≤100 时，先按"是否精确前缀匹配"分组（精确匹配排前），组内再按 rid 排序；或对 1-2 字母查询限制只匹配 kana/roma 的首音节而非全前缀，确保 "sh" 能找到新宿
6. **消除 buildIndex 的 1,120ms TBT**：把索引预计算为二进制格式（构建时生成），前端直接反序列化；或把 buildIndex 移到 Web Worker 中后台执行，先渲染搜索框
7. **添加 Makefile + requirements.txt + CI**：`make data`（build_data.py）、`make test`（pytest + node:test）、`make deploy`；GitHub Actions push 时自动跑测试 + 数据覆盖率断言（station_count ≥ 8,900, kana_coverage ≥ 0.90）
8. **修复模态框 Escape 键 + 搜索框双清除按钮 + 详情页历史支持**：三个前端小 bug，一次 commit 可以全修
9. **给无结果态加引导文案**：显示"ひらがな・カタカナ・ローマ字・簡体漢字でも試してみてください" + 示例 chips
10. **添加首屏加载进度条**：`fetch` 的 `ReadableStream` reader 按字节更新 2px CSS 进度条，完成后淡出
11. **修复颜色对比度**：`--text-3` 从 `#9a9aa0` 调深到 `#767680`（对比度 4.5:1），或仅在非关键文本上使用
12. **消除双端归一化漂移**：把 JP_MAP、VOWEL_AFTER 等提取为 `data/normalize_rules.json`，Python 和 JS 各自写通用加载器，测试断言双端输出一致
13. **修复 `s12.py` 重复定义和循环依赖**：删除第一个 `load_s12()`（:15-16）；`join_ridership()` 改为接受 `eki` 参数
14. **版本号自动注入**：构建脚本读 git short hash 替换 `?v=N`，消除手动同步 4 处
15. **审视客流数据年份窗口**：考虑扩展到 2024（S12-25 已含），或在 UI 徽标中更突出显示年份（当前 `(2019年度)` 字号 10.5px 容易忽略）
16. **考虑 stations.json 按需加载 `per` 明细**：首屏数据从 812KB 降到 ~500KB，详情页打开时再 fetch 单个站的明细（~200B/站）
17. **设置 `aria-activedescendant`**：键盘 ↑↓ 导航时更新，让屏幕阅读器正确播报当前高亮项
18. **检查并修复 robots.txt**：Lighthouse 报告 56 个错误，可能是 CF tunnel 的默认 robots 覆盖了应用层
19. **添加 `@supports` fallback**：对 `dvh`、`gap` 等新 CSS 特性提供降级方案，确保 iOS 14 及以下可用
20. **清理 canon.json 冗余键**：2,324 个键不在任何站名/线路名中出现，增加传输体积（28KB），构建时应只保留实际出现的字符的映射

## 十一、总结

这个项目有一个**好的骨架**——数据管线的多源合并逻辑严谨，前端搜索是纯函数可测试的，UI 设计克制且功能性优先。验证套件用真随机抽样+种子保证可复现性，meta.json 有 sha256 校验——这些都是"把数据当回事"的工程实践。

但它**还没有完成**。SPEC 8 的 4 项可量化验收标准全部未达标，PWA 的离线功能在线上不存在，819 个站（包括高田馬場这样的大站）没有读音导致假名/罗马音搜索完全找不到。这些问题不是"锦上添花"的优化项，是核心功能的缺口。

最关键的三个行动项：
1. 修复 SW 缓存穿透（1 行代码）
2. Debug 读音匹配逻辑（高田馬場为什么会缺读音）
3. 修复短前缀搜索排序（"sh" 找不到新宿）

修完这三个，这个项目可以从"能用"变成"可靠"。
